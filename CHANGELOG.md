# Changelog

## V0.3.0 — 2026-09-24 15:30
### Changes
- **Add `--date-analysis`: extract dates from filenames/folder names, cross-checked against real timestamps, off by default** (asked directly: "date and time validations... in the folder path structure; in the file name; the actual file created and/or modified timestamps; the exif info" — planned via AskUserQuestion before building: folder-path dates attach to each file's own record rather than a new "folder" record type; "validation" means collect every date as plain data plus a small set of narrow, near-always-genuine flags rather than flagging every cross-source disagreement; an ambiguous numeric date reports both readings rather than guessing a convention)
  - New `filenavlib/dateanalysis.py`: `find_dates_in_text()` tries an ordered set of regex patterns (ISO date+time, a weekday-month-time-year compound pattern, month names, plain ISO dates, ambiguous numeric, compact `YYYYMMDD`, and a low-confidence bare-year fallback) against a filename or single folder name, never overlapping a substring an earlier, higher-confidence pattern already claimed. Every candidate carries a `"confidence"` (`high`/`medium`/`low`), since a fixed pattern set can't be exhaustive against real-world filenames and the bare-year fallback especially will occasionally false-positive.
  - Applies to both real files (`scanner.py`) and archive entries (`archives.py`, using the entry's *internal* path, not the container's real filesystem ancestors). `date_analysis` is only added to a record when there's actually something to report — matching the project's existing lean-output convention for `"image"`/`"video"`.
  - Two deliberate performance choices, both following from the tar O(n²) hashing fix earlier: folder-path dates are computed once per directory in `walk_root()` (every file in a directory shares the same ancestors), and archive-internal folder segments are memoized per archive in `process_archive_file()`.
  - `compute_flags()` is deliberately narrow: `future_date` (after the scan's own start time) and `default_epoch_date` (within 2 days of 1970-01-01/1980-01-01/1601-01-01 — a tolerance window, not an exact match, since a timestamp converted to local time can land a day to either side of a UTC epoch value depending on timezone; caught by a real test failure on this machine's own UTC-5 timezone before shipping). Does **not** flag `created > modified` or a capture date that differs from the file's own timestamps — both are normal for a copied/migrated file and would flag almost every archived photo.
  - `summary.date_analysis_flagged` / `options.date_analysis` for visibility; verified end-to-end against real dated folder/file names on this machine, including the exact `backup-mon-aug-12-09_15_41-2019.tar`-style filename seen on a real drive during earlier testing.

## V0.2.2 — 2026-09-20 13:40
### Changes
- **Add `--archive-media` to extract EXIF/video metadata for images/videos found inside archives, off by default** (asked directly: "do images inside zip files still get checked for exif or similar data" — confirmed they didn't, a known limitation since V0.1.0; user chose "listed but not expanded" semantics and asked for it as an opt-in option)
  - Reuses the existing on-disk `media.get_image_info()`/`get_video_info()` functions unchanged, pointed at a temp file holding the member's decompressed bytes instead of a real file — so archive members now get the exact same `"image"`/`"video"` metadata shape (dimensions, EXIF date/GPS/camera, video duration) a loose file on disk already does.
  - zip/7z/rar extract each qualifying member on demand via the existing generic `_extract_member_to_temp()` (safe to reopen per-member for these formats). Tar computes it during the *same* single sequential pass `_list_tar_entries()` already makes for hashing — reading a matching member's bytes once (bounded by the existing `--max-hash-size-mb` cap) and reusing them for both the hash and the media extraction, instead of a second per-member `tarfile.open()` that would reintroduce the exact O(n²) reopening cost just fixed above.
  - Off by default: decompressing every image/video member found is real added cost on a scan with a lot of archived photos/videos, so this stays opt-in rather than changing the default `--archive-media`-off behavior.
  - `summary.archive_media_extracted` counts how many members got metadata this way; `options.archive_media_metadata` records whether it was on. Verified against real images in all three independent code paths (zip, tar, and 7z), including confirming the tar hash still comes out correct after the bytes-reuse refactor.
- **Fix the scan hanging indefinitely on a password-protected `.7z`/`.rar`** (reported directly, and correctly guessed the cause: "i think it was on a 7z file that requested a password to open" — confirmed exactly from the diagnostic log: stuck on `AcuDataProcessing_password_nacu.7z` for 28+ minutes until interrupted, with zero progress logged in between)
  - Every 7z-CLI subprocess call (`_run_7z()` in `archives.py`, used for listing and for extracting a nested-archive member; the `-so` streaming extraction `Popen` in `hash_member()`, used when a member has no precomputed CRC) never set `stdin=`, so the child process inherited the real console's stdin. An archive with encrypted headers needs a password just to *list* its filenames, not only to extract — 7z prints "Enter password (will not be echoed):" and blocks reading from stdin, and in an unattended run nobody is there to type one, so it waits forever.
  - Both call sites now set `stdin=subprocess.DEVNULL`. Verified directly: with stdin closed, 7z hits immediate EOF trying to read the password, prints "Break signaled", and exits with a clean non-zero code in well under a second instead of hanging.
  - Also added `config.SEVEN_ZIP_TIMEOUT_SECONDS` (300s) as a second, defense-in-depth layer via `subprocess.run(..., timeout=...)` on the listing call, in case some other kind of stall occurs — `stdin=DEVNULL` is the actual, verified fix for the reported case, this is just a backstop.
  - New end-to-end regression test builds a *real* password-protected `.7z` (via the system's own 7-Zip, `-mhe=on` for encrypted headers) and scans it, asserting the whole run completes in well under the 300s ceiling and the archive is recorded as a normal file with a clear error, instead of hanging.
  - Only `.7z`/`.rar` were at risk, since both route through the 7z CLI. Zip's password-protection can't hang the same way — `zipfile` has no interactive prompt at all, an encrypted entry just raises `RuntimeError` immediately, already caught by `hash_member()`'s existing error handling. Tar has no password-protection concept at the format level.
- **Fix O(n²) tar member hashing — a real scan got stuck ~25 minutes on one 143,770-entry `.tar.bz2`, at ~50s per small file** (diagnosed directly from the new diagnostic log after the user interrupted a run that "looked... slow for files that look too insignificant to cause a slowdown, and too often" — the new logging is exactly what made this diagnosable)
  - `hash_member()` for `"tar"` reopened the archive fresh — `tarfile.open(path)` then `tf.extractfile(entry["name"])` — for **every single member**. A compressed tar (`.tar.gz`/`.tar.bz2`/`.tar.xz`) isn't seekable: reaching member N means decompressing the entire stream again from byte zero, every time. That's O(n²) over the member count, scaling with the archive's *total* decompressed size, not the size of the file being hashed — exactly why tiny source files were each taking 45-100+ seconds: the file itself was never the expensive part. At the observed rate, this one archive was on pace to take months.
  - `_list_tar_entries()` now iterates the `TarFile` object directly (`for member in tf`, not `tf.getmembers()` up front) and extracts+hashes each file member the moment it's encountered, in the same single sequential pass that already reads every header — stashed as `precomputed_hash` on the entry. `hash_member()` checks for that field first and returns it directly, the same way it already did for zip's free CRC32, instead of reopening. Cost drops back to one sequential pass (what listing alone already cost), not one pass per member.
  - New regression test asserts `tarfile.open` is called **exactly once** (via monkeypatch) while processing a multi-member tar, so this can't silently regress; verified separately against a real compressed 3,000-member `.tar.bz2` (1.5s total, vs. what would have been unbounded growth under the old per-member-reopen behavior).
  - Known remaining case, not fixed here since it wasn't the cause of this incident: `_extract_member_to_temp()` for tar (used only when a tar member is itself a nested archive needing recursion) still reopens per call.
- **Add `--no-expand-formats {zip,tar,7z,rar} [...]` to record an archive file without opening it** (asked directly, after the tar incident above: "how can I exclude .tar files ... I would like an option to skip them" — clarified to mean the archive file itself should still be recorded (path/size/hash/dates), just not opened and enumerated)
  - Different from `--exclude-paths`/`--ignore-dirs`, which drop the file from the output entirely — this keeps the archive's own file record (including its normal file hash) but skips `archives.process_archive_file()` for it, so none of its internal members are enumerated.
  - `tar` covers every tar variant as one choice (`.tar`, `.tgz`, `.tbz2`, `.txz`, `.tar.gz`, `.tar.bz2`, `.tar.xz`), since `detect_archive_format()` already normalizes all of them to `"tar"`.
  - A skipped archive's record gets `"archive_expansion_skipped": true` alongside its existing `"archive_format"`. New `summary.archives_not_expanded` (separate from `summary.archives_expanded`) and `options.no_expand_formats` record what happened.
  - Verified end-to-end against real `.tar`/`.tar.gz`/`.tar.bz2`/`.tar.xz`/`.zip` files: all four tar variants recorded as plain files with no internal entries when `--no-expand-formats tar` is set; the `.zip` control was unaffected and still fully expanded.
- **Fix a real resource leak in nested-archive cleanup, likely the cause of a reported scan that "got slower and slower... almost not moving"**
  - `archives._extract_member_to_temp()` extracts a nested archive's member (e.g. a zip inside a zip) into a fresh `tempfile.mkdtemp()` directory; cleanup afterward removed `shutil.rmtree(os.path.dirname(extracted_path), ...)` — the member's *immediate parent* directory. Whenever the member's own internal name has a subdirectory component (ordinary in real zips, e.g. `docs/manual.zip`), that only deletes the innermost subfolder and leaves the actual `mkdtemp()` directory itself behind, permanently, for every such nested archive found — one leaked directory per nested archive for the rest of a run. On a large real-world scan (software installers, downloaded archives, etc. routinely bundle nested zips with folder structure) this could accumulate a large number of stale directories in the scratch temp folder over a long run, plausibly explaining a progressive slowdown that never actually crashed.
  - `_extract_member_to_temp` now returns `(extracted_path, dest_dir)`; the caller removes `dest_dir` itself, not a path derived from the extracted file.
  - Added a regression test building a zip whose nested-archive member lives under a subdirectory path, confirming the scratch directory ends up completely empty afterward.
- **Add a diagnostic log (`<output>.log`), separate from the errors log** (asked directly: the last run seemed stuck and got progressively slower, with no way to debug it)
  - New `filenavlib/scanlog.py` configures a `"filenav"` logger: `INFO`+ (or `DEBUG`+ with `-v`/`--verbose`) to the sidecar log file, `WARNING`+ also echoed live to the console.
  - Logs one line per directory entered (`filenavlib/scanner.py`) and per archive expanded (`filenavlib/archives.py`) by default — directories are far fewer than files, so this stays affordable even on a whole-drive scan, while still pinpointing exactly where a hang occurred: the log's last line is whatever was in flight when it stopped. `--verbose` adds a line per file too.
  - New `--slow-threshold-seconds` (default 10): logs a `WARNING` naming the exact file whenever a single hash, archive listing, or archive-member extraction/hash takes longer than this.
  - New `--log-interval` (default 60s, `0` disables): a periodic `INFO` heartbeat with running totals, the processing rate since the last heartbeat, and — specifically to catch leaks like the one just fixed — the scratch temp folder's current entry count, so a number that keeps climbing across heartbeats (rather than staying near zero) points straight at a resource leak instead of just "something is slow."
  - `summary.log_file` records the log's path; it gets the same `yyyy-mm-dd-hh-mm-ss_` timestamp prefix and directory as the output/error-log files, and is excluded from the scan the same way they are.
- **Fix the default ignore list not applying inside archives** (reported directly: `__pycache__` folders showing up in scan output despite being in the default ignore list)
  - The ignore-dir-name filtering (`.git`, `__pycache__`, `node_modules`, etc.) only ever applied to real filesystem directories walked by `filenavlib/scanner.py` — archive contents enumerated by `filenavlib/archives.py` had no filtering at all. Any zip/tar/7z/rar containing an ignored folder internally (a Python wheel or sdist bundling its own `__pycache__`, a downloaded repo export containing `.git/`, ...) leaked every one of those entries into the output regardless of the ignore list, since the two code paths never shared this logic.
  - New `archives._is_ignored_entry()` checks every directory segment of an archive member's internal path against the same `ignore_dir_names` set scanner.py uses, applied symmetrically to every archive format and every nesting depth. `summary.archive_entries_skipped_ignore_list` reports how many were filtered.
  - The `.filenav-skip` marker-file convention has no equivalent inside an archive (there's nowhere to put a marker file) and still only applies to real folders — this fix is specifically about the *default ignore list*.
- **Add `--config PATH` to read options from a JSON file, including extra ignore folders and the output filename itself**
  - New `filenavlib/configfile.py` (`load_config`) validates a JSON object against a schema (type-checked per key; a bare string is accepted as shorthand for a one-item list on `root`/`ignore_dirs`) and raises a clear error — before any scanning starts — for an unrecognized key, a wrong type, a missing file, or invalid JSON.
  - Precedence, per option independently: a value given explicitly on the command line always wins; otherwise the config file's value is used; otherwise the built-in default applies. Implemented correctly (not via the common but flawed "compare the parsed value to the default" heuristic, which breaks whenever the CLI value happens to match the default) by giving every layered `argparse` option `default=argparse.SUPPRESS` and layering `filenav.ARG_DEFAULTS` → config file → only the CLI keys actually present in `vars(args)`.
  - The output filename (previously a required positional) is now optional on the CLI — it can come from the config file's `"output"` key instead, with the same command-line-wins precedence; it's a clear error if neither supplies one.
  - `options.config_file` in the output JSON records which config file (if any) was used.
- **Add `--exclude-paths PATTERN [PATTERN ...]` for path/pattern-based exclusion, alongside the existing name-based `--ignore-dirs`** (asked directly: is exclusion name-based or path-based — and then to add path/pattern-based exclusion)
  - `--ignore-dirs` matches a folder's exact *name*, applied anywhere in the tree — it can't target one specific location, or match a naming pattern rather than an exact name. `--exclude-paths` fills that gap: glob patterns (`*`, `?`, `[seq]`, via stdlib `fnmatch`) matched against a file or folder's **full path**. A folder match excludes its whole subtree (same as `--ignore-dirs`); a file match excludes just that file — new for this mechanism, since name-based ignoring only ever applied to directories.
  - New `scanner.matches_any_pattern()`, used both by `should_skip_dir()` (top-of-loop check and the eager `dirnames[:]` pruning, mirroring how `ignore_dir_names` is already applied) and by a new per-file check alongside the existing self-output-file check.
  - `*` matches any characters including path separators (plain `fnmatch` glob semantics, not `.gitignore`-style `**`); either `\` or `/` works in a pattern on Windows, since `fnmatch` normalizes both the path and the pattern the same way (case-fold + slash-to-backslash) before comparing.
  - Scoped to real filesystem paths only, consistent with `.filenav-skip` — does not reach inside archives (unlike the default ignore list, which was just extended to archives above).
  - `summary.directories_skipped_via_path_pattern` / `files_skipped_via_path_pattern` report how many were skipped; `options.exclude_path_patterns` records the patterns in effect.
- **Default the output filename to `output.json` instead of requiring it** (asked directly, after using `--config` with no `"output"` key: "what is the output file then?")
  - The positional `OUTPUT` argument and `--config`'s `"output"` key both stay fully optional and take priority exactly as before; only the final fallback changed, from a hard error to `DEFAULT_OUTPUT_FILENAME = "output.json"`. It goes through the exact same `resolve_output_path()`/timestamp-prefix handling as any other filename, so it still lands next to `filenav.py` and still gets the `yyyy-mm-dd-hh-mm-ss_` prefix unless `--no-timestamp-prefix` is passed.
  - `filenav.py` (no other arguments at all) and `filenav.py --config myscan.json` (a config file with no `"output"` key) now both run successfully instead of erroring out.

## V0.2.1 — 2026-09-20 09:45
### Changes
- **Fix a single bad record crashing (and discarding) an entire multi-hour scan** (reported directly: a full `C:\` scan died at ~381k files/6.5 minutes in)
  - Root cause: `json.dumps(..., ensure_ascii=False)` happily stringifies a Python string containing lone surrogate code points (which real archive member names can decode to — Python's `tarfile` in particular falls back to `errors="surrogateescape"` for non-UTF-8 names), but writing that string to a UTF-8 file then raises `UnicodeEncodeError: 'utf-8' codec can't encode characters ...: surrogates not allowed` — and that exception was completely unhandled, killing the process and leaving an invalid, unparseable, truncated JSON file. All the work done up to that point was lost.
  - `filenavlib/writer.py` now sanitizes every string field before writing (round-tripping any unrepresentable character through `surrogateescape`/`replace`, so only the handful of actually-broken characters become `<0xFFFD>` — normal Unicode text, accented names, emoji, etc. is completely unaffected and still written as real readable characters, not escaped).
  - Defense in depth, since a whole-drive scan will keep surfacing surprises: `filenavlib/scanner.py` now wraps each file's processing (including its archive expansion) in `try/except`, and `filenavlib/archives.py` now wraps each archive member's processing the same way — one bad file or archive member is logged to `errors` and skipped, never aborts the rest of the scan.
  - `filenav.py`'s top-level scan loop now also catches any exception (or Ctrl+C) that still somehow gets through, and finishes writing a syntactically valid JSON file regardless — `summary.aborted`/`summary.abort_reason` record that it happened, exit code is `1`, but everything scanned up to that point is preserved and loadable instead of thrown away.
- **Suppress hachoir's own console warnings during video metadata extraction**
  - hachoir prints parser warnings (`[warn] [Autofix] ...`) and errors directly to the console by default, which was cluttering scan output and made it look like something was failing when it wasn't. Set via `hachoir.core.config.quiet = True`.
- **Stream errors to a sidecar log file instead of an unbounded in-memory list** (asked directly: are problem files listed anywhere, and can a large scan run the script out of memory?)
  - Every error was already recorded in the output JSON's `errors` array, but that array was a plain Python list held fully in memory for the whole run — the one part of the design that didn't share the streaming-to-disk approach the `files` array already used, and so the one place scan-time memory could in principle grow without bound (e.g. a flaky network drive throwing permission errors across huge numbers of files).
  - New `filenavlib/errorlog.py`: `ErrorSink`, a drop-in replacement for the plain list (same `.append()` interface) that writes every error to a sidecar `<output>.errors.log` file immediately as it happens (one JSON object per line, flushed after every write so nothing is lost even if the scan aborts hard right after), while keeping only a capped sample (first 1000) in memory for the main JSON.
  - The main JSON's `errors` array is now that capped sample; `summary.errors` is the true total count (`errors.count`), `summary.errors_sample_truncated` says whether the sample left anything out, and `summary.error_log_file` points at the sidecar log.
  - Also fixed a related drift bug this surfaced: the total error count was separately hand-tracked via `stats["errors"] += 1` at each call site, but two call sites (`os.walk`'s own `onerror` callback, and an unreachable root) appended to `errors` without incrementing it — so the reported count could under-count the real number of errors. Removed the redundant counter entirely; `errors.count` (from `ErrorSink`, incremented on every single `.append()`) is now the one authoritative total.
- **Add a `yyyy-mm-dd-hh-mm-ss_` timestamp prefix on the output/error filenames, on by default**
  - Both filenames are now prefixed with the local time the scan started (24-hour format), e.g. `output.json` → `2026-09-20-14-05-30_output.json`, and its error log gets the identical prefix (`2026-09-20-14-05-30_output.errors.log`) since it's derived from the already-prefixed output path. Repeated runs against the same output name no longer collide or silently overwrite each other, and filenames sort chronologically in a folder of past scans.
  - `--no-timestamp-prefix` writes the exact filename given, unchanged (matches the previous behavior).

## V0.2.0 — 2026-09-20 02:00
### Changes
- **Add a default ignore list for noise directories, plus `--ignore-dirs`/`--no-default-ignores`**
  - Beyond the existing `.filenav-skip` marker, folders are now also skipped by *name* (case-insensitive, matched anywhere in the tree) against a built-in default list: version-control internals (`.git`, `.svn`, `.hg`), dev/build caches (`node_modules`, `__pycache__`, `.venv`, `venv`, `.tox`, `.mypy_cache`, `.pytest_cache`, `dist`, `build`), Windows system folders (`System Volume Information`, `$RECYCLE.BIN`), and editor config (`.vscode`, `.idea`) — all machine-generated noise rather than real user data, and normally either regenerable, permission-denied, or (for `.git`) thousands of tiny internal blob files that would otherwise dominate a scan.
  - `--ignore-dirs NAME [NAME ...]` adds more names on top of the default list; `--no-default-ignores` turns the default list off entirely (only `.filenav-skip` and any explicit `--ignore-dirs` still apply) for cases like deliberately wanting `.git` history included in a duplicate-file audit.
  - The output JSON's `options` now records `default_ignores_applied` and the exact `ignore_dir_names` set used for that run; `summary` now reports `directories_skipped_via_marker` and `directories_skipped_via_ignore_list` separately (previously one combined `directories_skipped_via_marker` count).
  - Matching subdirectories are pruned before `os.walk` descends into them (not just skipped once reached), avoiding a wasted directory listing for each one.

## V0.1.0 — 2026-09-20 01:15
### Changes
- **Initial implementation of the filesystem inventory scanner**
  - `filenav.py` (CLI entry point) + `filenavlib/` (scanner, hashing, archive handling, media metadata, streaming JSON writer).
  - Walks one or more roots (default: `C:\`; `--root all` enumerates every ready Windows drive) recording, per file: full path, filename, created/modified timestamps, size in bytes, and a `sha256` hash (configurable via `--hash-algo`) for validation and duplicate matching. Files above `--max-hash-size-mb` (default 2048) are recorded without a hash rather than reading the whole thing.
  - Folders containing a file named `.filenav-skip` are excluded entirely, along with every file and subfolder beneath them.
  - **Archive expansion**: `.zip` and `.tar`/`.tar.gz`/`.tar.bz2`/`.tar.xz` are read via the standard library; `.7z` and `.rar` via the system's 7-Zip CLI (auto-detected on PATH or at `C:\Program Files\7-Zip\7z.exe`, gracefully degraded to "file only, contents not listed" if absent). An archive nested inside another archive (zip-in-zip-in-zip, a zip inside a 7z, etc.) is extracted to a scratch temp folder and recursed into, up to `--max-archive-depth` (default 10) levels; each member's recorded `path` shows the full container chain (`outer.zip // inner.zip // file.txt`). Zip members reuse the format's own built-in CRC32 (free — no need to decompress); 7z/rar members use the CRC 7-Zip's own listing reports; tar members (no built-in checksum) are hashed by streaming their content, same size cutoff as regular files.
  - **Image metadata** (Pillow): dimensions, EXIF capture date, camera make/model, and GPS coordinates (converted to decimal degrees) when present.
  - **Video metadata** (hachoir, pure Python — no ffmpeg/external binary needed): duration, dimensions, recording date, and device/producer info when the container exposes it.
  - Output is streamed to the JSON file record-by-record (not built up in memory first), so a full-drive scan with millions of files doesn't blow up RAM.
  - The output JSON file is passed as a parameter and, per the spec, always gets one final self-referencing entry in its own `files` array (`"self_reference": true`) — its `size_bytes` is captured immediately before the closing JSON is appended (documented as a close approximation, since a file can't know its own exact final size while still being written), and its content is never parsed/analyzed.
  - Output path resolution: a bare filename (`results.json`) is written next to `filenav.py`; a filename with any path component (relative or absolute) is used as given.
  - Full pytest suite (`tests/`) covering the skip-marker rule, hash correctness and the size cutoff, recursive nested-zip expansion (with CRC verification), output-path resolution, and an end-to-end CLI run producing valid JSON with the expected self-record.

### Known limitations (not addressed this pass)
- `.rar` (and `.7z`) contents require 7-Zip to be installed on the machine running the scan; without it those files are still recorded, just without their internal member list. Password-protected/encrypted archives of any format are recorded as a plain file with an error noted, not opened.
- Image/video metadata extraction only applies to files sitting directly on disk — an image or video found *inside* an archive is recorded (path/size/hash) but its EXIF/duration/etc. is not extracted, to avoid extracting every archived file during a whole-drive scan.
- `--root all` drive auto-enumeration is Windows-only (uses `GetLogicalDrives`/`GetDriveTypeW`); on other platforms it falls back to scanning `/`.
- "Created" timestamp uses `os.stat().st_ctime`, which is genuinely the file creation time on Windows/NTFS (this project's target environment) but means "last metadata change" on Linux/macOS.
